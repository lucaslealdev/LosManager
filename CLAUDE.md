# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Los Manager is a desktop management system for "Los Pastelles" (a Brazilian pastelaria/food business), built with Python + CustomTkinter. It handles products, customers, orders, cash register (caixa), reports, and thermal receipt printing. The UI text, variable names, and comments are in Portuguese (pt-BR) — keep new code consistent with that convention.

## Running the app

```
python main.py
```

No virtual environment or dependency manifest is checked in. Required third-party packages (install as needed): `customtkinter`, `Pillow` (`PIL`), `pywin32` (`win32print`, used by `utils/impressora.py`). Standard library only otherwise.

There is no test suite, linter, or formatter configured in this repo.

## Building the Windows executable

```
build.bat
```

This installs PyInstaller, cleans `build/`/`dist/`, and runs `python -m PyInstaller LosManager.spec --clean`. The output is `dist/LosManager/` — that whole folder must be copied together (no Python install needed on the target machine). `LosManager.spec` bundles `assets/` and collects `customtkinter` data files; `win32print`/`win32ui`/`win32con`/`win32timezone` are declared as hidden imports since PyInstaller can't detect them automatically.

If invoking this from Git Bash (not a native Windows shell): run it as `./build.bat < /dev/null`, not `cmd /c build.bat` or `cmd //c build.bat`. Both `cmd /c` forms get mangled by MSYS path conversion of the `/c` flag and silently fail to run the script (either "not recognized" or a no-op interactive `cmd` session) without a nonzero-looking failure that's obvious from the transcript — always check the resulting `dist/LosManager/LosManager.exe` timestamp to confirm a rebuild actually happened. The `< /dev/null` redirect is needed because the script ends with `pause`, which otherwise waits on stdin.

## Architecture

**Entry point**: `main.py` defines `LosManager(ctk.CTk)`, the main window. It builds a left sidebar menu and a right content area. Each menu button swaps the content area's contents by destroying existing widgets (`limpar_area`) and instantiating a screen class into `self.area`. There is no routing/state framework — navigation is just "destroy everything in the frame, build a new one."

**Caixa gate (the app is locked while no caixa is open)**: `utils/caixa_estado.py` (`buscar_caixa_aberto()` / `esta_aberto()`) is the single query for "is there an open caixa". It lives in `utils/` rather than on the Caixa screen because `main.py` needs it too, and importing a screen from `main` just for that would be circular — `Caixa.buscar_caixa_aberto()` delegates to it so the query exists in one place. `main.py`'s `navegar()` refuses any `chave` other than `"caixa"` while no caixa is open: it warns (`messagebox.showwarning`) and redirects to the Caixa screen, and `criar_interface()` starts the app on Caixa instead of Dashboard in that state. So a closed caixa means the only reachable screen is Caixa — **Configurações included**, which is deliberate (the startup update check and the auto-installer run from `LosManager.__init__`, before any navigation, so they're unaffected by the block). `Pedidos.finalizar()` repeats the check on its own before calling `gravar_pedido()`, covering the case where the caixa is closed while the Pedidos screen is already built.

**`screens/`**: one module per feature area, each exposing a `ctk.CTkFrame` subclass instantiated by `main.py` (`Dashboard`, `Produtos`, `Ingredientes`, `Clientes`, `Pedidos`, `Caixa`, `Relatorios`, `Configuracoes`). These are self-contained: each screen queries the database directly, builds its own widgets, and owns its own CRUD/dialog logic (typically via `ctk.CTkToplevel` popups and `tkinter.messagebox` for confirmations/errors). There's no shared service/repository layer between screens and the database — SQL lives inline in each screen.

**Responsive screens (`utils/responsivo.py`)**: every screen with a big `ttk.Treeview` list (Produtos, Ingredientes, Clientes, Relatórios, the Pedidos cart) is expected to size that table dynamically instead of hardcoding `height=N` rows, so the list actually fills the available space at any window size down to the 1200x700 minimum, rather than leaving dead space or forcing the page's `CTkScrollableFrame` to scroll. The technique, and the reasoning behind it, lives entirely in `utils/responsivo.py`:
- `linhas_para_tabela(tela, scroll, pady_tabela=..., ...)` computes a row count by *measuring* real widget sizes (`winfo_reqheight` + `pack_info()` pady) of everything else already packed into the screen's `CTkScrollableFrame`, rather than guessing pixel budgets — guessing was tried first and consistently left either a small scrollbar or wasted space, because a `CTkScrollableFrame`'s inner content never gets stretched or shrunk by its canvas (only its width is fitted; height is always exactly the natural size of its children) and its rounded corners eat a few px that must be subtracted from `winfo_height()` too. Callers must pass `pady_tabela` matching whatever `pady` the table itself will be `.pack()`ed with, or the math is off by exactly that amount.
- `tornar_dinamica(tela, scroll, obter_tabela, **kwargs)` is what makes this hold up during actual use, not just at the moment the screen opens: it binds a debounced `<Configure>` handler on the root window that recalculates and re-`configure()`s the table's `height` as the user resizes — pass `excluir=(tabela,)` semantics are handled internally so the table's own current size never pollutes the recalculation of its next size. The binding self-removes once the screen frame is destroyed (checked via `winfo_exists()`), so navigating away and back doesn't stack up dead handlers on the root window.
- Call both when building a new list screen: compute the initial `linhas_para_tabela(...)` right before creating the `Treeview` (with every above-the-table — and, if applicable, below-the-table — widget already packed, so it's included in the measurement), then call `tornar_dinamica(...)` right after `.pack()`ing the table. See `screens/relatorios.py` and `screens/pedidos.py` for the pattern used when content comes *after* the table too (build and pack that trailing content first purely to measure it, then insert the table above it with `pack(before=...)`).
- This only applies to the row-count of tables; it is not a general dynamic-layout/font-scaling system, and screens without a big table (Caixa, Configurações, Dashboard) aren't expected to use it.

**`database/conexao.py`**: a single `Banco` class wrapping one shared SQLite connection, instantiated once as the module-level singleton `banco` and imported everywhere (`from database.conexao import banco`). It auto-creates all tables (`categorias`, `produtos`, `clientes`, `pedidos`, `itens_pedido`, `caixa`, `movimentos_caixa`, `enderecos_cliente`, `ingredientes`, `receita_produto`, `movimentos_ingrediente`) on construction, and exposes generic helpers: `executar` (write, auto-commits), `executar_sem_commit`/`commit`/`rollback` (manual transactions, for multi-statement writes that must be all-or-nothing — see `Pedidos.gravar_pedido()`), `buscar` (fetchall), `buscar_um` (fetchone), `ultimo_id` (lastrowid). Screens call these directly with raw SQL rather than going through an ORM. The `configuracoes` key/value table is created lazily by `utils/config.py` instead of `Banco.criar_tabelas`.

**Ingredient stock (recipe-based inventory)**: `produtos` still has its own flat `estoque` column (finished-good count), but products that are made of components (e.g. a pastel with multiple fillings) can additionally declare a *recipe*: `receita_produto` links a `produto_id` to one or more `ingrediente_id` rows with a `quantidade` (in that ingredient's own `unidade_medida` — there is no unit-conversion logic, so recipe quantity and ingredient stock must already share units). `ingredientes` is the standalone ingredient stock table (`estoque_atual`, `estoque_minimo`, `custo_unitario`, soft-deleted via `ativo` when still referenced by a recipe, same pattern as `produtos`). Recipes are edited from `screens/produtos.py`'s `JanelaReceita` popup (button "🧂 Receita do Produto Selecionado"). `Pedidos.gravar_pedido()` deducts both `produtos.estoque` *and* every recipe ingredient's `estoque_atual` inside the same manual transaction as the order write, logging each deduction to `movimentos_ingrediente` (`tipo='saida'`, tied to `pedido_id`). Before adding an item to a cart, `Pedidos.verificar_estoque_ingredientes()` sums recipe consumption across the whole cart (an ingredient can be shared by several products) and either warns (default) or blocks (if `utils.config.bloquear_venda_sem_estoque_ingrediente()` is on, toggled from Configurações) when stock would go negative. `screens/dashboard.py` shows a banner naming any ingredient at or below `estoque_minimo`.

**Order cancellation**: `Relatorios.cancelar_pedido()` (button "🚫 Cancelar Pedido Selecionado") is the only cancellation path — it's a soft cancel (`pedidos.status` set to `'Cancelado'`, row kept for history) guarded against double-cancel by checking the current status first, and requires the admin password (`config.obter("senha_reset")`, same password used by the "zerar pedidos" danger zone) before the confirmation dialog. `Relatorios.devolver_estoque_pedido()` is the exact inverse of the deduction in `Pedidos.gravar_pedido()`: for each `itens_pedido` row it adds the quantity back to `produtos.estoque`, then walks that product's `receita_produto` and adds back to each ingredient's `estoque_atual`, logging an offsetting `movimentos_ingrediente` row (`tipo='devolucao'`). Both run inside one manual transaction (`executar_sem_commit` + `commit`/`rollback`), same pattern as order creation. Cancelled orders stay in `Relatorios`' list (grayed out via the `"cancelado"` Treeview tag) but are excluded from the summary cards (pedidos count / vendas / taxa motoboy / ticket médio) so a cancelled sale doesn't inflate reported revenue — `screens/caixa.py`'s daily summary applies the same exclusion (filters `p.status != 'Cancelado'` after fetching, since a cancelled order's cash was already returned to the customer). The bulk "zerar pedidos" danger-zone actions hard-delete `pedidos`/`itens_pedido`/`movimentos_ingrediente` together (no stock is returned there — it's a full history wipe, not a cancellation). `Relatorios.reverter_cancelamento()` (button "↩️ Reverter Cancelamento") undoes a mistaken cancel: same password gate, only acts on a row whose status is currently `'Cancelado'`, flips it back to `'Finalizado'`, and `reconsumir_estoque_pedido()` re-deducts product/ingredient stock — the exact inverse of `devolver_estoque_pedido()` (mirrors `Pedidos.gravar_pedido()`'s original deduction, logging `movimentos_ingrediente` with `tipo='saida'` again), same manual-transaction pattern.

**Date picker (`utils/calendario.py`)**: `escolher_data(master, ao_escolher, data_inicial=None)` opens `JanelaCalendario`, a month-grid popup built from stdlib `calendar` + CustomTkinter buttons — deliberately *not* `tkcalendar`, which would be a new third-party dependency to install per machine and declare as a PyInstaller hidden import. The callback receives a `"dd/mm/aaaa"` string, the same format `pedidos.data` is stored in, so filtering is a plain string compare. It follows the deferred-sizing rule below (`self.after(60, self._ajustar_tamanho)`). `Relatorios` uses it for its "📅 Escolher data" filter: when a date is set it *overrides* the Período segmented button (they're alternative filters, never combined), and clicking any período clears it via `selecionar_periodo()`.

**Viewing an order's items**: `Relatorios.ver_pedido()` (button "🔍 Ver Pedido") opens `JanelaDetalhePedido`, a read-only popup listing what was sold in the selected order — product, per-item observation, qty, unit price, subtotal — plus the vendas/motoboy/total breakdown, and a "PEDIDO CANCELADO" banner when applicable. Same deferred-sizing pattern as the other popups.

**Screen width budget (1366x768)**: the shop's PC is 1366x768, and after the sidebar and paddings a screen's content area is only ~1040px wide. A row of widgets packed `side="left"` that needs more than that silently pushes its last widgets off-screen — this actually shipped once (the "Remover selecionado" button in Pedidos disappeared after an entry was added to its row). Two rules that follow: keep a row's total requested width under ~1040px, splitting into a second row inside its own `CTkFrame` when needed (the frame also isolates its widths from the parent `grid`'s column sizing), and always give a long explanatory `CTkLabel` a `wraplength` — without one it stretches its row to the full text width (one such label was forcing a row to ~1900px). Checking a change is mechanical: build the screen under a `1366x768` root and assert every `self.scroll` child's `winfo_reqwidth()` fits.

**Per-item observations**: `itens_pedido.observacao` holds a free-text note attached to one cart line (e.g. "retirar o milho" on a pastel that normally comes with corn) — it is per *item*, not per order (`pedidos.observacao` is the separate order-wide field). It's typed into the "Obs. do item" entry next to Qtd in `screens/pedidos.py`, shown as its own column in the cart `Treeview`, cleared after each `adicionar_item()`, and written by `gravar_pedido()`. On the receipt, `utils/impressora.py`'s `_bloco_destacado()` prints it right below its product in **reverse video** (ESC/POS `GS B 1`/`GS B 0`, white on black), padding each line to the full paper width so the black bar spans the whole line instead of stopping where the text ends — the point is that the kitchen can't miss it. The Configurações test print includes an observation on purpose so a new printer can be checked for reverse-video support.

**Schema migrations**: there's no migration framework — `Banco.criar_tabelas()` just runs `CREATE TABLE IF NOT EXISTS` for everything, every startup. When a table needs one-time data migration from an older shape (e.g. `enderecos_cliente`, added to let a client have multiple addresses instead of one set of address columns on `clientes`), the pattern is: check whether the new table already existed *before* creating it, and if not, run a one-time migration copying data out of the old columns/shape. The old columns are left in place afterward (not dropped) — cheaper and safer than an `ALTER TABLE ... DROP COLUMN`, and nothing reads them going forward. Follow this same check-then-migrate-once pattern for future schema changes. For adding a *column* to a table that already exists in production DBs, `CREATE TABLE IF NOT EXISTS` is not enough — use `Banco._garantir_coluna(tabela, coluna, tipo)`, which checks `PRAGMA table_info` and issues the `ALTER TABLE ... ADD COLUMN` only when it's missing (idempotent, runs every startup). Keep queries naming columns explicitly rather than `SELECT *` so added columns never shift positional indexes.

**`utils/config.py`**: persistent app settings stored as key/value rows in the `configuracoes` table (store name/address/phone, printer name, paper width) — this exists so store/printer info doesn't need to be hardcoded per machine. Also owns the frozen-vs-source path resolution used throughout the app:
- `caminho_base()` — folder for *external* files (the SQLite `.db`), which intentionally sits next to the `.exe`, not bundled inside it.
- `caminho_recursos()` / `caminho_asset()` — folder for files *bundled* into the PyInstaller package (assets like icons/logos), resolved via `sys._MEIPASS` when frozen.

`database/conexao.py` has its own near-identical `_caminho_base()` for the same frozen-vs-source distinction — keep both in sync if that logic changes.

**`utils/tema.py`**: the single source of truth for brand colors (`COR_LARANJA`, `COR_TEXTO`, etc.) and `ttk.Treeview` styling. Also defines a "compatibility" block of old color name aliases (`COR_MARROM`, `COR_SALMAO`, ...) kept so older screen code doesn't break — prefer the current names in new code.

**`utils/impressora.py`**: builds and sends ESC/POS raw byte commands to a Windows-installed thermal printer via `win32print` (RAW spooler job), independent of printer brand. `montar_cupom()` composes the receipt bytes (store header + logo bitmap + items + totals) from plain dicts; `imprimir_cupom()` sends it, pulling printer name/paper width from `utils/config.py` if not passed explicitly. Paper width in chars: 32 = 58mm, 48 = 80mm.

**External network call**: `screens/clientes.py` looks up addresses by CEP (Brazilian postal code) via the public ViaCEP API (`urllib.request` in a background `threading.Thread`, JSON parsed with `json.loads`) so the UI doesn't freeze while waiting on the network.

**Versioning**: semantic (`MAJOR.MINOR.PATCH`). The root `VERSION` file (tracked in git, plain text, e.g. `1.0`) holds MAJOR.MINOR and is bumped by hand only when a change actually warrants it — everything else about the release process is automatic. PATCH is always `github.run_number`, so every push still produces a unique, ordered version with zero manual bookkeeping per release.

**Update checking (`utils/atualizacao.py`)**: the GitHub Actions workflow (`.github/workflows/build-release.yml`) computes `MAJOR.MINOR.PATCH` (`VERSION` file + `github.run_number`) right before the PyInstaller step and writes it to `assets/versao.txt` (gitignored — only exists inside a CI-built `.exe`, never in source or hand-built copies) and uses the same string for the release tag (`vX.Y.Z`), so it gets bundled and is readable at runtime via `config.caminho_asset("versao.txt")`. `atualizacao._parsear_versao()` turns both the local file and the GitHub tag into an `(int, int, int)` tuple — comparing tuples, not strings, avoids the classic `"1.0.9" > "1.0.10"` bug. On startup, `main.py` calls `atualizacao.verificar_silenciosamente()` (no-op unless `sys.frozen`, i.e. running from source never checks) which hits `https://api.github.com/repos/ramonxxl/LosManager/releases/latest` on a background thread and only interrupts the user (`messagebox.askyesno` → `webbrowser.open`) if a newer version actually exists; any network/parse failure is swallowed on purpose so a launch never breaks over connectivity. `screens/configuracoes.py` also exposes `atualizacao.verificar_manualmente()` behind a button, which — unlike the silent variant — always calls back with either a result or an error, since the user asked for it explicitly. **This requires the GitHub repo to stay public**: the release API 404s for unauthenticated requests against a private repo, which would make every check silently fail forever with no way to tell from inside the running app.

**Auto-update (`utils/autoatualizador.py`)**: complements `atualizacao.py` — that one only *checks* whether a newer version exists; this one downloads the release `.zip` and replaces the installed files by itself, so the user no longer has to open the browser and swap the folder by hand. Only meaningful from a frozen `.exe` (there's no "installation" to replace otherwise). Windows won't let a running `.exe` overwrite itself, so the flow is: download + unzip into a temp folder, write a `.bat` that waits for this PID to disappear, `robocopy` the new files over `config.caminho_base()` and relaunch, fire that script detached, then `os._exit(0)`. The `robocopy` deliberately runs **without** `/MIR` or `/PURGE` — it only overwrites and adds, never deletes, because `losmanager.db` and `backups/` sit next to the `.exe` but aren't part of the release zip, and a mirror would wipe them. `JanelaAtualizacao` is the modal progress popup (no close button — the app is about to restart itself). `iniciar(master, url_download)` is the entry point, used both by the startup prompt in `main.py` and by the Configurações button.

## Conventions to follow

- Screen classes follow a consistent internal layout: `__init__` calls a sequence of `montar_*`/`criar_*` builder methods; section breaks are marked with `# ====...====` comment banners.
- Database access is inline raw SQL through the shared `banco` singleton — do not introduce an ORM or a new connection; add queries directly in the relevant screen (or `utils/config.py`-style module for settings).
- Path resolution must always go through `utils/config.py`'s `caminho_base`/`caminho_recursos`/`caminho_asset` helpers (or the equivalent in `database/conexao.py`) so both dev (`python main.py`) and frozen (`.exe`) execution keep working.
- New persistent settings belong in the `configuracoes` key/value table via `utils/config.py`, not as new hardcoded constants.
- Screens are responsive and new ones should be too: any screen with a big list `Treeview` must size it with `utils/responsivo.py`'s `linhas_para_tabela` + `tornar_dinamica` instead of a hardcoded `height=N` — see the "Responsive screens" note above for the technique and why.
- Anything that records money or stock movement must check `caixa_estado.esta_aberto()` before writing. The menu already gates navigation, but a screen that can sit open while the caixa is closed (Pedidos) needs its own check too — see the "Caixa gate" note above.
